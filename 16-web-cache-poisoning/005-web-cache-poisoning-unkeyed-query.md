# Lab: Web cache poisoning via an unkeyed query string

## 개요

- **난이도**: Practitioner
- **주제**: Web Cache Poisoning — Unkeyed Query String / 쿼리 반영 XSS / 캐시 버스터 헤더
- **링크**: https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws/lab-web-cache-poisoning-unkeyed-query

## 목표

쿼리스트링이 캐시 키에 포함되지 않는 결함을 이용해 홈 페이지 캐시를 오염시키고, 방문자(Chrome 사용자) 브라우저에서 `alert(1)` 을 실행시킨다.

## 취약 지점

### 1. 쿼리스트링이 캐시 키에 없음 (unkeyed query string)

```
정상이라면 Cache Key = path (+ query)
이 랩에서는 query 가 키에 포함되지 않음

  GET /?a=1  → cache hit
  GET /?b=2  → cache hit (같은 항목)
→ 쿼리만 바꿔서는 별도 캐시가 만들어지지 않음
```

### 2. 쿼리가 응답에 반영됨

```
캐시 miss 시, 주입한 파라미터가 응답에 반영됨
  (예: canonical 링크 등에 현재 URL/쿼리 반영)
→ 응답에 XSS 페이로드를 심을 수 있음
```

### 3. 캐시되면 쿼리 없이도 페이로드 유지

```
오염된 응답이 캐시에 저장되면
  GET / (쿼리 없음) 로도 페이로드가 담긴 응답이 반환됨
→ 정상 사용자가 피해
```

## 분석 도구

```
[캐시 키 확인]
  Pragma: x-get-cache-key
  → 응답에 캐시 키가 표시됨 (일부 랩에서 지원)

[캐시 버스터]
  쿼리는 키에 없으므로 쿼리로는 cache-buster 불가
  → "키에 포함되는 헤더" 를 cache-buster 로 사용
  이 랩에서는 Origin 헤더가 keyed
```

## 공격 단계

### 1단계 — unkeyed query 확인

홈 페이지 요청에 임의 쿼리를 붙여도 `X-Cache: hit` 인지 확인한다.

```
GET /?a=1
GET /?b=2
→ 둘 다 캐시 히트 → 쿼리는 unkeyed
```

### 2단계 — 캐시 버스터 설정

쿼리 대신 `Origin` 헤더를 cache-buster 로 사용한다.

```
GET /?a=1
Origin: https://example.com
```

### 3단계 — 반영 확인

cache miss 응답에서 주입한 파라미터가 응답에 반영되는 것을 확인한다.
오염되면 쿼리를 제거한 요청에도 반영된 내용이 캐시로 남는다.

### 4단계 — XSS 페이로드 주입

반영 문자열을 탈출하는 페이로드를 쿼리에 넣는다.

```
GET /?evil='/><script>alert(1)</script>
```

응답에 페이로드가 반영되고 `X-Cache: hit` 가 날 때까지 재전송한다.

### 5단계 — 피해자 시뮬레이션

쿼리를 제거하고 같은 cache-buster(Origin)로 요청해, 캐시된 페이로드가 그대로 오는지 확인한다.

```
GET /
Origin: https://example.com
→ 캐시된 응답에 alert(1) 포함
```

### 6단계 — 실제 사용자 대상 오염

`Origin` cache-buster 를 제거하고 다시 페이로드를 쿼리에 넣어 재전송해,
**일반 사용자용 캐시 키**를 오염시킨다. 브라우저에서 홈 페이지를 열어 팝업을 확인한다.

### 7단계 — 유지

캐시가 약 35초마다 만료될 수 있으므로, 피해자가 방문해 랩이 풀릴 때까지 재오염을 반복한다.

## 캐시 키 결함의 관점

```
[핵심 질문]
  "이 입력이 응답에 영향을 주는가?"  → 그렇다
  "그 입력이 캐시 키에 포함되는가?"  → 아니다
  → 캐시 오염 성립

[여기서는 입력 = 쿼리스트링]
  쿼리가 응답(반영)에 영향을 주지만 키에는 없음
  → 같은 경로의 캐시를 악성 응답으로 덮어씀
```

## 방어

```
[근본 원인]
  1) 쿼리스트링이 응답에 반영되는데 캐시 키에는 미포함
  2) 반영 시 안전한 인코딩 부재 (XSS)
  3) 응답 캐싱

[올바른 방어]
  1. 캐시 키 정규화/정확성
     - 응답에 영향을 주는 쿼리 파라미터를 반드시 캐시 키에 포함
     - 불필요 파라미터는 무시하지 말고 키 설계를 명확히
  2. 반영 값의 출력 인코딩/살균
     - canonical/URL 등 반영 지점의 컨텍스트 인코딩
  3. 캐시 제어
     - 동적/개인화 응답은 no-store, 필요한 경우 Vary 활용
  4. 프레임워크/프록시의 캐시 키 처리 점검 (Pragma: x-get-cache-key 등)
  5. CSP 로 인라인 스크립트 완화

[주의]
  "쿼리가 캐시 키에서 제외된다" 는 설계는 반영 지점과 만나면 곧바로 취약점이 된다.
```

## 핵심 정리

- 쿼리스트링이 캐시 키에 없어, 쿼리로 페이로드를 주입해 홈 페이지 캐시를 오염시킬 수 있었다.
- 쿼리로는 cache-buster 가 안 되므로 `Origin` 헤더(keyed)를 cache-buster 로 사용했다.
- 오염 후 쿼리 없는 `GET /` 요청에도 `alert(1)` 이 담긴 응답이 캐시로 반환되어 방문자가 피해를 봤다.
- 방어는 응답에 영향을 주는 입력을 캐시 키에 포함하고, 반영 값 인코딩과 캐시 제어를 적용하는 것이다.

## 배운 점

- 앞선 랩(헤더/쿠키)과 달리, 이번 취약 입력은 **쿼리스트링**이었다.
- 캐시 키에 포함되지 않는 입력은 무엇이든 공격 표면이며, 키에 포함되는 다른 입력(헤더)을 cache-buster 로 쓴다.
- `Pragma: x-get-cache-key` 같은 진단 헤더로 캐시 키를 직접 확인할 수 있다.
- 이후 랩은 캐시 파라미터 클로킹, 키 정규화 등 더 정교한 구현 결함으로 확장된다.
