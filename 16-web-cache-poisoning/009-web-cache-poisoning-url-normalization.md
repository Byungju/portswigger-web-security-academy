# Lab: URL normalization

## 개요

- **난이도**: Practitioner
- **주제**: Web Cache Poisoning — URL 정규화(Normalization) / 반사형 XSS + 브라우저 URL 인코딩 우회
- **링크**: https://portswigger.net/web-security/web-cache-poisoning/exploiting-implementation-flaws/lab-web-cache-poisoning-normalization

## 목표

404 페이지의 반사형 XSS 는 브라우저가 URL 을 인코딩해 직접 실행되지 않는다. 캐시의 **URL 정규화**를 이용해 브라우저의 인코딩된 요청이 오염된 캐시 항목에 적중하도록 만들어 `alert(1)` 을 실행시킨다.

## 취약 지점

### 1. 404 경로 반사형 XSS

```
GET /random
→ "random" 경로가 에러 메시지에 반영됨

GET /random</p><script>alert(1)</script><p>foo
→ 경로가 반사되어 XSS 성립 (Burp 로 직접 보내면 실행)
```

### 2. 브라우저는 URL 을 인코딩

```
브라우저 주소창에 위 URL 을 입력하면
  <  >  /  등이 %3c %3e %2f 등으로 인코딩되어 전송
→ 서버가 디코딩하지 않으면 페이로드가 그대로 실행되지 않음
```

### 3. 캐시가 URL 을 정규화(디코딩)해 키를 생성

```
[Burp 로 보낸 요청(원시)]
  GET /random</p><script>alert(1)</script><p>foo
  → 캐시 키 계산 시 URL 디코딩 → 동일 키로 저장

[브라우저가 보낸 요청(인코딩)]
  GET /random%3c%2fp%3e%3cscript%3ealert(1)%3c%2fscript%3e%3cp%3efoo
  → 캐시가 디코딩해 같은 키로 조회 → 오염된 캐시 항목 적중
```

즉, 캐시의 정규화(디코딩)로 **다른 표현의 URL 이 같은 캐시 키**가 되어,
브라우저가 보낸 인코딩 요청이 우리가 심어둔 악성 응답을 받는다.

## URL 정규화(Normalization)란

```
캐시/프록시가 캐시 키를 만들기 전에 URL 을 "정규형" 으로 바꾸는 처리
  - 퍼센트 인코딩 디코딩      (%3c → <)
  - 대소문자 통일            (/Admin → /admin)
  - . / .. (dot-segment) 해소
  - 중복 슬래시 정리          (//a → /a)
  - 후행 슬래시 처리
  - 기본 포트 제거

[문제]
  캐시의 정규화 규칙과 백엔드의 URL 해석 규칙이 다르면
  서로 다른 URL 이 같은 키로 충돌하거나, 반대로 같은 URL 이 갈라짐
  → 캐시 오염/디셉션
```

## 공격 단계

### 1단계 — 반사형 XSS 확인

존재하지 않는 경로로 요청해 경로가 에러 메시지에 반영되는지 확인한다.

```
GET /random
```

### 2단계 — 페이로드 삽입

```
GET /random</p><script>alert(1)</script><p>foo
```

Burp Repeater 로 보내면 응답에 스크립트가 반영된다.

### 3단계 — 브라우저 인코딩으로 직접 실행 안 됨 확인

같은 URL 을 브라우저 주소창에 입력하면 `%3c` 등으로 인코딩되어 페이로드가 실행되지 않는다.

### 4단계 — 캐시 오염

Burp 로 페이로드 요청을 보내 캐시에 저장하고, **즉시** 브라우저로 같은 URL 을 연다.
캐시가 URL 을 디코딩해 같은 키로 조회하므로, 오염된 응답(실행되는 스크립트)을 받아 `alert()` 가 뜬다.

### 5단계 — 피해자 전달

캐시를 재오염시키고 즉시 **Deliver link to victim** 으로 악성 URL 을 전달한다.
피해자가 링크를 방문하면 오염된 캐시 응답으로 `alert(1)` 이 실행된다.

> 캐시가 만료되기 전에 전달해야 하므로, 재오염 후 즉시 전달한다.

## 방어

```
[근본 원인]
  1) 404 경로가 출력 인코딩 없이 반영 (XSS)
  2) 캐시와 백엔드의 URL 정규화 규칙 불일치
  3) 정규화된 키로 인해 다른 표현이 같은 캐시 항목을 공유

[올바른 방어]
  1. 반사 값 출력 인코딩
     - 경로/URL 을 HTML 컨텍스트에 맞게 이스케이프
  2. 정규화 일관성
     - 캐시와 백엔드가 동일한 정규화 규칙 사용
     - 정규화는 "라우팅/보안 판단 이후" 가 아니라 일관된 단계에서
  3. 캐시 키 설계
     - 정규화 결과를 키에 반영하되, 백엔드 해석과 어긋나지 않게
  4. 리다이렉트로 정규형 URL 을 강제해 표현을 하나로 통일
  5. CSP 로 스크립트 실행 완화

[주의]
  정규화는 편의 기능이지만, 캐시와 백엔드가 조금만 달라도
  캐시 오염/캐시 디셉션의 원인이 된다.
```

## 핵심 정리

- 404 경로 반사 XSS 는 브라우저가 URL 을 인코딩해 직접 실행되지 않았다.
- 캐시가 URL 을 디코딩(정규화)해 키를 만들기 때문에, 브라우저의 인코딩 요청이 Burp 로 심은 오염 캐시에 적중해 스크립트가 실행됐다.
- 재오염 후 즉시 피해자에게 링크를 전달해 랩을 풀었다.
- 방어는 반사 값 인코딩과 캐시/백엔드 정규화 규칙 일치다.

## 배운 점

- 007(`;` 파싱), 008(fat GET)에 이어, 이번에는 **URL 정규화 불일치**가 오염 벡터였다.
- 캐시 오염은 "캐시와 백엔드가 같은 요청을 다르게 해석하는 모든 지점" 에서 발생한다.
- 브라우저의 자동 인코딩은 서버측 취약점을 막지 못하며, 정규화 계층이 이를 무력화할 수 있다.
- 정규화 규칙(디코딩/대소문자/dot-segment/슬래시)은 캐시 오염·캐시 디셉션 진단의 핵심 점검 항목이다.
