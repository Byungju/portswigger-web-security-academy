# Lab: 2FA simple bypass

## 개요

- **난이도**: Apprentice
- **주제**: Authentication — 다중 인증(MFA) / 2FA 단순 우회 / 강제 브라우징(Forceful Browsing)
- **링크**: https://portswigger.net/web-security/authentication/multi-factor/lab-2fa-simple-bypass

## 목표

비밀번호까지는 알고 있지만 2FA 코드는 모르는 `carlos` 계정에 대해, 2FA 검증을 건너뛰고 계정 페이지에 접근한다.

- 내 계정: `wiener:peter`
- 피해자 계정: `carlos:montoya`

## 다중 인증(MFA) 기초

```
[인증 요소의 종류]
  1) 알고 있는 것 (Something you know)   : 비밀번호
  2) 가지고 있는 것 (Something you have) : OTP 앱, SMS, 하드웨어 토큰
  3) 본인인 것 (Something you are)       : 생체 인증

[2FA]
  위 요소 중 2개를 요구 (보통 비밀번호 + OTP)

[정상 흐름]
  1단계: username + password 검증
  2단계: 2FA 코드 검증
  3단계: 완전히 인증된 세션 부여 → 보호된 페이지 접근 허용
```

### 취약점이 생기는 지점

```
비밀번호 검증 직후, 2FA 검증 전 상태를
"인증된 것" 으로 취급하거나,
보호된 페이지가 "2FA 완료" 여부를 확인하지 않으면
→ 2FA 단계를 건너뛰고 접근 가능
```

## 취약 지점

### 인증 상태(State) 관리 미흡

```
[로그인 1단계 성공 시 서버 동작 (추정)]
  비밀번호 확인 → 세션 발급
  302 Location: /login2   ← 2FA 입력 페이지

[문제]
  이 세션은 "비밀번호만 통과한" 불완전한 상태인데,
  /my-account 는 세션 존재 여부만 확인하고
  "2FA를 완료했는가" 는 확인하지 않음

[결과]
  2FA 페이지 대신 /my-account 로 직접 이동하면
  계정 페이지가 그대로 열림
```

```
[인증 단계]
  비밀번호 통과 ──→ (2FA 대기) ──→ 2FA 통과 ──→ 완전 인증
        │                                            │
        │  세션 발급                                  │
        └──────────── 직접 /my-account ──────────────┘
                     (2FA 확인 없이 접근)
```

즉, 서버가 "2단계를 거쳤는지" 를 세션 상태로 강제하지 않고,
클라이언트가 2FA 페이지를 거칠 것이라고 가정한 것이 원인이다.

## 공격 단계

### 1단계 — 본인 계정으로 흐름 파악

`wiener:peter` 로 로그인한다. 2FA 코드가 이메일로 발송되며 `/login2` 로 이동한다.
이메일 클라이언트에서 코드를 확인해 2FA 를 통과한다.

### 2단계 — 계정 페이지 URL 확인

계정 페이지의 URL 을 확인한다.

```
https://LAB-ID.web-security-academy.net/my-account
```

### 3단계 — 로그아웃 후 피해자로 로그인

로그아웃하고 피해자 자격증명으로 로그인한다.

```
username=carlos&password=montoya
```

2FA 입력 화면(`/login2`)으로 리다이렉트된다. (코드는 알 수 없음)

### 4단계 — /my-account 로 강제 이동

2FA 코드를 입력하지 않고, 주소창/프록시에서 URL 을 직접 변경한다.

```
GET /my-account HTTP/1.1
Cookie: session=<비밀번호까지만 통과한 세션>
```

2FA 검증 없이 carlos 의 계정 페이지가 로드되면 랩 해결.

## 강제 브라우징(Forceful Browsing)

```
[정의]
  접근 흐름(UI/링크)을 우회해
  보호된 URL 에 직접 접근을 시도하는 것

[이번 랩에서의 의미]
  "2FA 를 통과해야 /my-account 에 도달한다" 는 것은
  UI 상의 흐름일 뿐,
  서버가 검증하지 않으면 직접 접근으로 우회된다

[일반 원칙]
  UI/단계 흐름은 보안 경계가 아니다.
  보호 자원은 서버가 상태를 확인해 강제해야 한다.
```

## 방어

```
[근본 원인]
  2FA 완료 여부를 서버가 강제하지 않음
  → 불완전 인증 상태의 세션으로 보호 페이지 접근 가능

[올바른 방어]
  1. 인증 상태를 서버 세션에 명확히 저장
     - session.auth_stage = "password_ok" / "fully_authenticated"
  2. 모든 보호 엔드포인트에서 완전 인증 여부 확인
     - "fully_authenticated" 가 아니면 /login2 로 강제
     - /my-account 등은 2FA 미완료 시 접근 불가
  3. 2FA 미완료 상태에서는 2FA 외 다른 기능 접근 금지
  4. 인증 완료 시에만 세션을 "완전 인증" 으로 승격
     - 가능하면 2FA 완료 전에는 세션을 발급하지 않거나,
       제한된 임시 세션으로 분리
  5. 민감 기능 접근 시 서버 측 인가/상태 검사 일관 적용 (deny by default)

[안티패턴]
  "클라이언트가 /login2 를 거칠 것" 이라는 가정
  비밀번호 검증 직후 완전한 세션 부여
  UI 에서만 2FA 페이지로 유도하고 서버는 확인하지 않음
```

## 핵심 정리

- 비밀번호 통과 후 세션이 발급되지만 2FA 완료 여부가 서버에서 강제되지 않았다.
- 2FA 입력 대신 `/my-account` 로 직접 이동해 carlos 의 계정 페이지에 접근했다.
- 이는 인증 상태 관리 미흡으로 인한 강제 브라우징(Forceful Browsing) 우회다.
- 방어는 세션에 인증 단계를 저장하고, 보호 엔드포인트마다 완전 인증 여부를 검사하는 것이다.

## 배운 점

- 2FA 는 "코드 검증" 자체보다 "검증 완료 상태를 서버가 강제하는가" 가 핵심이다.
- UI 흐름(리다이렉트)은 보안 통제가 아니며, 서버 측 상태 검사로 대체되어야 한다.
- 이 랩은 1번(단순 인증 우회)과 달리, 자격증명이 있어도 2FA 라는 추가 단계를 논리 결함으로 건너뛴 사례다.
