# Lab: Using application functionality to exploit insecure deserialization

## 개요

- **난이도**: Apprentice
- **주제**: Insecure Deserialization — 애플리케이션 기능 악용 / 직렬화 데이터 신뢰 / 파일 삭제(경로 조작)
- **링크**: https://portswigger.net/web-security/deserialization/exploiting/lab-deserialization-using-application-functionality-to-exploit-insecure-deserialization

## 목표

세션 쿠키의 직렬화 객체를 수정해 애플리케이션의 **계정 삭제 기능**이 `carlos` 홈 디렉터리의 `morale.txt` 파일을 삭제하게 만든다.

- 계정: `wiener:peter`
- 백업 계정: `gregg:rosebud`

## 배경 개념 — "애플리케이션 기능 악용" 유형

직렬화 취약점을 익스플로잇하는 방식은 여러 가지다.

```
[익스플로잇 유형]
  1) 객체 속성 변조        → 권한 상승 (001: admin=b:1)
  2) 데이터 타입 변조      → 인증 우회 (002: access_token=i:0)
  3) 애플리케이션 기능 악용 → 이 랩
     - 매직 메서드/가젯 체인 없이,
       앱이 "정상적으로 제공하는 기능" 이 직렬화 데이터를 입력으로 받아
       위험한 동작을 수행하게 만든다.
```

```
[이 랩의 구조]
  계정 삭제 기능(POST /my-account/delete)은
  직렬화 객체의 avatar_link(아바타 파일 경로)를 참조해 파일을 삭제한다.

  즉, 삭제 동작은 정상 기능이지만
  그 대상 경로가 "클라이언트가 조작 가능한 직렬화 데이터" 에서 온다.
  → avatar_link 를 carlos 의 morale.txt 로 바꾸면 그 파일이 삭제된다.
```

## 취약 지점

```
[근본 원인]
  1) 파일 경로를 클라이언트 세션(직렬화 객체)에 저장 → 공격자가 임의 변경 가능
  2) 계정 삭제 시 그 경로를 검증 없이 그대로 사용 (delete/unlink 등 위험 메서드 호출)
  3) "내 아바타" 라는 소유권/경계 검사(경로가 내 디렉터리인지)가 없음

[전형적 코드(개념)]
  function deleteAccount($user) {
      unlink($user->avatar_link);   // ← 직렬화 데이터의 경로를 그대로 사용
      deleteUser($user->username);
  }
```

```
[핵심]
  공격자가 넣는 것은 "코드" 가 아니라 "데이터(경로)" 다.
  앱의 정상 기능이 그 데이터를 신뢰하고 위험한 동작을 대신 수행한다.
```

## 공격 단계

### 1단계 — 계정 삭제 기능 확인

로그인 후 "My account" 페이지에서 계정 삭제 기능이
`POST /my-account/delete` 로 요청됨을 확인한다.

### 2단계 — 세션 쿠키 디코딩

세션 쿠키를 Burp Inspector 로 디코딩하면 직렬화 객체에
`avatar_link` 속성(아바타 파일 경로)이 있음을 확인한다.

```
O:4:"User":2:{s:8:"username";s:6:"wiener";s:11:"avatar_link";s:??:"<아바타 경로>";}
```

### 3단계 — avatar_link 를 carlos 파일로 변경

`avatar_link` 값을 `/home/carlos/morale.txt` 로 바꾸고,
**길이 접두어도 23 으로 갱신**한다.

```
[변경 전]
s:11:"avatar_link";s:<원래길이>:"<아바타 경로>";

[변경 후]
s:11:"avatar_link";s:23:"/home/carlos/morale.txt"
```

> `/home/carlos/morale.txt` 는 23바이트다. 값을 바꾸면 반드시 `s:` 길이를 맞춰야 한다.

### 4단계 — 삭제 요청 전송

"Apply changes" 후 요청 라인을 `POST /my-account/delete` 로 바꿔 전송한다.

```
POST /my-account/delete HTTP/1.1
Cookie: session=<변조된 직렬화 객체>

→ 내 계정이 삭제되면서, avatar_link 가 가리키는
  /home/carlos/morale.txt 도 함께 삭제됨 → 랩 해결
```

## 직렬화 데이터 신뢰와 서버 측 검증 — 방어 관점 조사

### 1. 직렬화 데이터를 "입력" 으로 취급해야 한다

```
세션 쿠키는 사용자가 볼 수 있고 바꿀 수 있는 입력이다.
  001/002 에서는 그 데이터로 "권한/신원" 을 판단해 문제가 됐고,
  이 랩에서는 그 데이터로 "파일 경로" 를 결정해 문제가 됐다.

[일반화]
  직렬화된 클라이언트 데이터는 언제나 변조 가능하다고 가정해야 한다.
  그 값을 신뢰하는 "모든 곳" 이 공격면이 된다. (권한, 신원, 경로, 금액, 등급 ...)
```

### 2. 위험한 메서드를 사용자 입력에 직접 실행하지 않는다

```
이 랩의 sink: 파일 삭제(unlink/delete) 같은 위험한 동작
  - 위험 동작의 "대상" 을 클라이언트 데이터에서 직접 받으면 안 된다.
  - 서버가 사용자 ID 로부터 경로를 "재구성" 하고, 그 결과만 사용해야 한다.
```

### 3. 인증(Authentication)과 인가(Authorization)를 서버에서

```
[인증] 요청 주체가 누구인가 → 서버 측 세션에서 확정
       (클라이언트 쿠키의 username/is_admin 을 믿지 않는다)
[인가] 그 주체가 이 동작/이 자원에 접근 가능한가 → 매 요청 검사
       (예: "아바타 삭제는 내 디렉터리 내부 경로만 허용")
[이 랩의 결여]
  삭제 대상 경로가 정말 "요청한 사용자 소유" 인지 확인하지 않았다.
```

### 4. 경로 검증 (Path Traversal 방지와 동일 원리)

```
  - 허용 베이스 디렉터리(예: /home/<user>/) 밖으로 벗어나는지 검사
  - 정규화(canonicalize) 후 접두어 검사, `..`/심볼릭 링크 차단
  - 사용자 입력 경로를 OS 명령/파일 API 에 직접 전달하지 않기
```

## 방어

```
[근본 원칙]
  직렬화 데이터(클라이언트 쿠키)를 신뢰하지 않는다.
  인증/인가는 항상 서버에서, 서버가 소유한 상태로 판단한다.

[구체적 방어]
  1. 서버 측 세션
     - 신원/권한/파일경로 등 권위 있는 값은 서버 저장소에 두고,
       쿠키에는 무의미한 세션 ID 만 저장.

  2. 서버 측 재구성 + 검증
     - 파일 경로는 서버가 사용자 ID 로부터 구성하고,
       정규화 후 허용 디렉터리 내부인지 검사.
     - 소유권/경계 검사를 통과한 경우에만 위험 동작 실행.

  3. 위험 동작 최소화/격리
     - delete/unlink 등 위험 메서드는 최소 권한으로, 격리된 프로세스에서.
     - 대상은 신뢰할 수 있는 서버 상태에서만 결정.

  4. 안전한 역직렬화
     - 신뢰 불가 입력은 역직렬화하지 않는다 (JSON 등 데이터 전용 포맷 + 스키마 검증).
     - 불가피하면 HMAC/서명으로 무결성 보증 + allowed_classes 화이트리스트 + 엄격 타입 검사.

  5. 권한 모델 명확화
     - 모든 상태 변경 기능에 대해 "누가 이 자원에 무엇을 할 수 있는가" 를 서버에서 강제.
```

## 핵심 정리

- 계정 삭제 기능이 직렬화 객체의 `avatar_link` 경로를 그대로 사용해 파일을 삭제했다.
- `avatar_link` 를 `/home/carlos/morale.txt`(23바이트)로 바꾸고 길이 접두어를 맞춘 뒤 `POST /my-account/delete` 를 보내 carlos 의 파일을 삭제했다.
- 매직 메서드/가젯 체인 없이 **앱의 정상 기능을 공격자의 데이터로 유도**하는 유형이다.
- 근본 원인은 "조작 가능한 직렬화 데이터를 신뢰" + "서버 측 소유권/경계 검사 부재" 이며, 방어는 서버 측 세션/재구성 + 인가 검사 + 경로 검증이다.

## 배운 점

- 직렬화 데이터의 신뢰는 권한(001), 타입(002)뿐 아니라 **파일 경로 같은 동작 대상**에서도 문제가 된다.
- 위험한 메서드(sink)는 사용자 입력을 직접 대상으로 삼아서는 안 되며, 서버가 재구성·검증한 값만 사용해야 한다.
- 인증(누구인가)과 인가(무엇을 할 수 있는가)는 항상 서버 측에서 판단해야 한다. 클라이언트 쿠키의 값은 신뢰할 수 없다.
- 001~003 을 관통하는 공통 원칙: **신뢰할 수 없는 입력을 역직렬화하지 않고, 그 데이터로 인가/동작을 결정하지 않는다.**
